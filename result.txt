FINDING 1 — REAL DEFECT (low severity, not previously known) — NOW FIXED
  Unknown subcommands exited 0 instead of erroring.

    BEFORE                                   AFTER
    serv-kun nginx bogus-subcommand      -> 0      -> 1
    serv-kun postgres bogus-subcommand   -> 0      -> 1
    serv-kun springboot bogus-subcommand -> 0      -> 1
    serv-kun ssh bogus-subcommand        -> 0      -> 1
    serv-kun bogus-top-level             -> 1      -> 1   (was always correct)

  The four parent commands printed help and exited 0 when handed an
  unrecognised subcommand, so a typo in a script under `set -e` — say
  `serv-kun postgres backupp` — succeeded silently having backed nothing up.

  The obvious fix does not work, and this is worth recording. Setting
  `Args: cobra.NoArgs` alone changes nothing: cobra checks Runnable() *before*
  it validates arguments, so a parent with no Run at all returns "print help"
  and the Args validator is never reached. The parent must ALSO be given a
  RunE to become runnable. Both halves are required.

  This nearly shipped as a non-fix. A first attempt set only NoArgs and was
  "verified" by a unit test that called parent.Args(...) directly — which
  passed, because calling the validator by hand bypasses the very Runnable()
  short-circuit that made the bug possible. Only re-running the real binary
  exposed that nothing had changed. The test has been rewritten to execute the
  actual command tree via rootCmd.Execute(), so it now fails if the binary
  regresses.

  Fixed in: cmd/{nginx,postgres,springboot,ssh}.go (Args + RunE),
            cmd/root.go (showHelp, parentCommands)
  Covered by: cmd/root_test.go — 8 tests including a guard that fails if a new
            grouping command is added without being registered.

  Cosmetic side effect: making the parents runnable adds a "serv-kun <parent>
  [flags]" line to their usage block alongside the existing "[command]" line.
  Accurate, if slightly noisier.

FINDING 2 — TEST TOOLING ARTIFACT, NOT A PRODUCT DEFECT
  "deploy.yml is valid YAML" reported [FAIL] in the compose suite. The cause
  was a bind-mount path that did not translate under Git Bash, so the parser
  container saw an empty directory. Re-run separately with a real YAML parser
  and a correct mount, deploy.yml and docker-compose.prod.yml both parse and
  every structural assertion passes — see the GENERATED YAML section (15/15).
  No action needed.

--------------------------------------------------------------------------------
NOT COVERED — read this before trusting the report
--------------------------------------------------------------------------------
These are honest gaps, not silent omissions:

  * RHEL / Fedora paths. Everything ran on Debian-family containers. The dnf
    branches in nginx/postgres/certbot/firewall install, the firewalld backend,
    and the wheel-group logic are exercised only by unit tests, never against a
    real RHEL host.
  * SELinux. Atomic writes replace an inode via rename; on an SELinux-enforcing
    host the new file's context derives from the parent directory. Very likely
    fine for /etc/ssh, but untested — containers here do not run SELinux.
  * ufw versus Docker-published ports. Documented in the README as a known
    limitation; proving it needs an external host to probe from, which this
    environment does not have.
  * Let's Encrypt issuance. certbot is never actually invoked against the ACME
    service — that needs a public domain and a reachable host, and repeated runs
    would burn real rate limits. The TLS bootstrap sequence is verified only by
    reading the code.
  * The `node` wizard. Installing nvm downloads from the network and mutates a
    user's home directory; skipped to keep the suite hermetic.
  * Multi-wizard flows needing root plus a real network (nginx setup end-to-end,
    springboot setup end-to-end, springboot deploy/rollback). Their components
    are covered individually; the full sequences are not.
  * Long-running behaviour. The 6-hourly nginx reload loop and the 24-hour
    backup cycle are verified as single iterations, not over real elapsed time.
